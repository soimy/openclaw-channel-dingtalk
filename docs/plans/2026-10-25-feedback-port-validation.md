# 社区新版卡片评价移植与验收

## 来源与实现

- 社区基线：`soimy/openclaw-channel-dingtalk` main，`232eb2d10d42e831e05f588429a52df3f8811232`。
- 参考实现：`RowanZhong/openclaw-channel-dingtalk` 固定提交 `62d95592365363ae021c1e58f0521c181077156f`；只移植反馈相关变更，保留 MIT 许可。
- 验收完成后，用户已明确授权本地提交；不推送远程。

实现覆盖原提问者点赞、点踩、撤销、原因提交，本人统计和私聊精确问答查询；默认关闭的 HTTP 快照上报使用本地持久化待办、按需 Worker、失败退避和重启恢复。发送内容仅包含最新评价及对应一问一答，接收端按记录与版本幂等处理，提交事务后 ACK。

移植时额外解决：

1. 保留社区新版 `ocx1.*` 扩展卡片的动作命名空间，不截获扩展自定义的 `feedback_up`。
2. 保留新版回复策略清理、停止及问答卡接管流程；空回答占位卡不能被标记为可评价。
3. SQLite 使用公开分页读取 API，限制每页、总字节和单条事件大小；拒绝代际变化、重复 ID、身份或指纹不一致。
4. 旧 JSONL 直接有界读取，避免调用新版会生成兼容导出文件的旧 SDK 路径 helper；正确处理 macOS `/var` 路径别名。
5. 2026.10 的 `agents.entries` 与较早版本 `agents.list` 共用配置投影；命令入口使用三个版本均支持的 `command-auth-native`。
6. 压力冷却结束后先采样完整周期，防止把“未采样”误认为资源恢复；不丢弃超过 1024 个并发前台操作的身份。
7. 真机发现新版宿主在空闲时 RSS 可超过 1GiB。将固定 RSS 门限改为实际可用内存与 Worker 预算，保留 cgroup 80%/CPU 压力限制，避免正常大进程永久暂停上报。

## 环境与隔离

验收跨 2026-10-25 至 2026-10-26（Asia/Shanghai）。宿主版本为 2026.8.1、2026.9.34、2026.10.7。后两者根据[官方发布列表](https://github.com/openclaw/openclaw/releases)和 npm 元数据选定，版本、完整性信息及锁文件保存在忽略的 `.local/`。依赖、pnpm 10.33.0、Node 24.22.1、缓存、测试工作区均位于项目内。

环境：macOS arm64，Apple M5，10 个逻辑 CPU，24 GiB 内存。本机同时运行其他项目。

- 首次检查既有网关占用 18789；用户随后授权临时切换该网关及钉钉配置。
- 原配置保存在 `.local/backups/openclaw.before-feedback.json`，恢复清单记录前后 SHA-256。
- 原 LaunchAgent 已停止，测试网关只管理本项目记录的 PID；每次切换先关闭当前网关，再检查 18789 空闲。
- 各版本使用 `.local/live/<version>/state`、`workspace`、`tmp`、`cache`；配置、模板和账号访问范围仅用于指定测试群与测试账号。
- 固定答案测试服务端口 58183；真实 HTTP / SQLite 事务接收端端口 58182。微基准接收器使用操作系统分配的空闲端口，实际端口在结果文件中。
- 同一个机器人只由一个网关连接。升级测试复制停止后的测试 Agent 数据，保持逻辑 `instanceId` 和接收目标不变，验证原问答与评价继续有效。
- 按用户要求保留临时配置，等待用户通知才还原。密钥、原配置、会话正文和原始真机日志不进入 Git。

## 性能结果

以下为 15 秒合成前台负载与真实 SQLite 上报模块探针。每 10ms 的计时探针记录额外延后，本地 ACK 指评价持久化耗时，不是钉钉网络往返或生产模型首字延迟。

| 宿主 | 前台探针 P99，关闭/开启上报 (ms) | 本地评价 P99，关闭/开启 (ms) | 前台期间 Worker / POST |
| --- | --- | --- | --- |
| 2026.8.1 | 2.20 / 2.19 | 9.58 / 9.38 | 0 / 0 |
| 2026.9.34 | 2.23 / 2.17 | 10.01 / 8.91 | 0 / 0 |
| 2026.10.7 | 2.16 / 2.16 | 8.78 / 9.68 | 0 / 0 |

空闲 SQLite 上报：三个版本均在 15 秒内提交 8/8 条记录，无失败，队列排空，空闲 Worker 回收。进程 RSS 峰值相对起始值增加约 95.1、92.8、134.2 MiB；这些样本包含 Worker 内加载宿主 SDK 的成本，不能声称零资源开销。

32 秒事件循环压力场景在前半段每 200ms 制造一次 75ms 卡顿。修复后，首次上报在压力结束约 4.6 秒后发生，8/8 条待办全部完成；修复前冷却期间可能提前启动 Worker，失败样本留在本地诊断目录。慢接收端场景会被前台活动中断并保留待办；超大转录返回 pending，不静默截断正文。

低可用内存与恢复的单元回归，以及同一 9.34 大 RSS 网关热加载后真实补传的证据均通过。最新 10.7 的真实 SQLite 慢接收端探针保留 8 条待办且终止 Worker；超大转录探针上报 8 条 pending 元数据，无失败且不静默截断。

原始测量：`docs/assets/feedback-port-2026-10-25/performance.json`。基准入口：

```bash
node scripts/build-feedback-benchmark.mjs .local/feedback-benchmark
node .local/feedback-benchmark/feedback-reporting-benchmark.mjs \
  --enabled --scenario pressure --seconds 32 --cards 8 \
  --output .local/feedback-pressure.json
```

真实 SQLite 基准使用 `--sqlite`，并在输出目录的 `node_modules/openclaw` 绑定待测宿主，同时通过独立 `OPENCLAW_STATE_DIR`、`OPENCLAW_CONFIG_PATH` 和 `XDG_CACHE_HOME` 隔离宿主状态。

## 真机执行记录

使用用户指定测试群、原提问者账号、另一名群成员，以及用户提供的原生 Feedback 模板。固定答案服务只替代模型生成，入站、卡片投放、点击回调、身份校验、宿主 SQLite、HTTP 和 SQL 接收端均真实运行。

### 2026.8.1：已完成

- 原提问者连续提出两个不同问题，得到相同固定答案，分别点赞和点踩并提交“内容不完整”原因。
- 本地记录保存不同的问题/回答消息 ID；接收数据库的正文分别对应各自原问题，均为 available，不含思考或整段会话。
- 用户确认本人统计为赞 1 / 踩 1，私聊详情对应第一问；分别撤销后赞踩均为 0。
- 另一成员真实尝试赞踩和原因，日志记录 forbidden；用户确认拒绝提示和统计正常。
- 接收端真实返回 503，原提问者重新点赞仍正常；待办记录 http_503。
- 干净停止并重启网关、恢复接收端后，无需再次点击，约 73 秒后自动补传第 3 版点赞并获 ACK；正文保留正确。

### 2026.9.34：已完成

已将停止后的测试 Agent 数据复制到独立目录。宿主要求迁移 schema 19 的会话身份；跨目录快照还需要显式恢复测试 Agent 的归属。使用该版本官方 `agents add` / `doctor --fix --non-interactive` 完成，缓存和临时目录限制在项目内。网关 running、connected 已确认。用户确认升级前旧卡片可撤销，新卡点赞、点踩、原因和另一成员拒绝均正常；接收端正文准确对应新卡各自原问题。另用该版本详情读取接口核对旧 8.1 问答及指纹一致。

真机额外发现固定 1GiB RSS 门限会让已保存的原因滞留。修复后，在同一网关进程仍高于 1GiB 的情况下热加载插件，自动补传第 2 版及两项原因，无需再次点击；详见 `high-rss-recovery.json`。

### 2026.10.7：已完成

使用独立 9.34 测试快照升级，宿主官方修复流程将 Agent 配置迁移为 `agents.entries`。用户确认旧 9.34 问答可精确查看，旧赞踩均可撤销，统计恢复为 0；新 10.7 卡片赞踩、原因面板与其他成员拒绝均正常。接收端新点赞为第 1 版、新点踩及原因为第 2 版，正文均为 available 且分别对应正确原问题。

最终真实数据：10 张关联卡片中有 6 张发生过评价，接收端仅有这 6 条记录，未评价卡片没有上报。六组正文均准确；最终四条旧评价为 none，两条新评价分别为 like/dislike。匿名汇总见 `docs/assets/feedback-port-2026-10-25/device-matrix.json`。
